# Домашнее задание к занятию "13.Системы мониторинга"

## Обязательные задания

1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя 
платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой 
осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы
выведите в мониторинг и почему?

**Ответ:**

**CPU Utilization (%):** Базовая метрика использования процессора. Показывает, насколько интенсивно нагружены ядра.

**Memory Utilization (%):** Вычисления могут потреблять значительный объём RAM. Контроль использования памяти помогает предотвратить OOM (Out Of Memory).

**Free Swap Space (%):** Если вычисления начнут вытесняться в swap, их производительность катастрофически упадёт из-за дискового I/O. Метрика служит индикатором нехватки физической памяти.

**Space Utilization (%):** Простое свободное место. Переполнение диска остановит генерацию новых отчётов.

**Free Inodes (%):** Даже при наличии свободного места в гигабайтах, исчерпание inode-ов (индексных дескрипторов) приведёт к ошибке создания нового файла. Это частая проблема сервисов, создающих множество мелких файлов.

**Disk Write / Read Request Avg Waiting Time (ms):** Среднее время ожидания операций ввода-вывода. Рост этой метрики напрямую указывает на то, что запись отчётов на диск стала узким местом и замедляет весь процесс.

**Загруженность интерфейсов (Bits received / sent):** Поскольку взаимодействие идёт по HTTP, важно видеть объём входящего и исходящего трафика. Это помогает понять пропускную способность и выявить аномалии.

**Rate (общее количество HTTP-запросов):** Интенсивность входящего потока. Показывает, с какой нагрузкой работает платформа.

**Errors (количество ошибочных запросов):** Число или доля запросов, завершившихся ошибкой (например, HTTP 5xx). Прямой индикатор проблем в вычислениях или при сохранении отчётов.

2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, 
что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы 
можете ему предложить?

**Ответ:**

**RAM** - Оперативная память. Если память кончается, вычисления тормозят или сервис падает.

**inodes** - «Слоты для файлов» в файловой системе. Можно иметь много свободного места, но закончились слоты — новый файл не создастся. Новые отчёты перестанут сохраняться.

**CPU Load Average** - Не «загрузка процессора», а очередь задач к процессору: сколько задач выполняется или ждёт. Если очередь растёт, отчёты считаются дольше, клиент ждёт.

Это стандартный язык «насколько мы выполняем обязанности перед клиентами».

SLI — что мы измеряем. Например: доля успешных запросов.

SLO — внутренняя цель. Например: 99,9% успешных запросов в месяц.

SLA — внешнее обещание клиенту, часто с последствиями. Например: 99,9% доступности и компенсация при нарушении.

4. Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. 
Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 
70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

**Ответ:**

Ошибка в том, что в знаменатель summ_all_requests попадают 3xx-редиректы, а в числитель — только 2xx. При отсутствии 4xx/5xx оставшиеся 30% — это редиректы. SLA надо считать как долю не-5xx ответов или включать 3xx в успешные, а также учитывать только финальные коды ответов, чтобы не двойной счёт после редиректов.

5. Опишите основные плюсы и минусы pull и push систем мониторинга.

**Ответ:**

Pull

+ Централизованный контроль частоты и целей

+ Сразу видна недоступность цели (up=0)

+ Проще отладка (curl на endpoint)

+ Хорошо работает с service discovery

+ Меньше риска перегрузки приёмника

− Нужна сетевая доступность цели

− Плохо для NAT/firewall

− Плохо для короткоживущих задач

− Нужен открытый защищённый endpoint

− Сервер мониторинга — потенциальное узкое место

Push

+ Работает через NAT/firewall

+ Удобно для batch и короткоживущих задач

+ Подходит для edge и распределённых сетей

+ Клиент может буферизовать и повторять отправку

+ Естественен для событий и логов

− Сложнее заметить «молчание» клиента

− Риск перегрузки коллектора

− Конфигурация размазана по клиентам

− Сложнее безопасность и аутентификация

− Возможны дубли и переупорядочивание

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.

Факультативно можете изучить какие метрики собирает telegraf после выполнения данного задания.
